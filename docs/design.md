# WindowShade 设计文档

本文件规定 WindowShade 的功能需求、所依据的 macOS 限制、目标架构、验证方法和改写顺序。
现有代码按本文件逐步改写。改写期间，代码与本文件不一致时以本文件为准；尚未改写的部分在第 8 节列出。

## 1. 术语

| 术语 | 含义 |
|---|---|
| 收起 | 用户双击标题栏后，原窗口从屏幕上移开，原位置显示卷帘条 |
| 展开 | 原窗口回到收起前的位置和大小，卷帘条移除 |
| 卷帘条 | 收起后显示在原窗口标题栏位置的窗口，内容为原标题栏的截图 |
| 原窗口 | 被收起的那个窗口，属于其他应用程序 |
| 看一眼 | 指针停在卷帘条上时，在卷帘条下方显示原窗口画面的功能 |
| 画面卡片 | “看一眼”显示原窗口画面的窗口 |
| 空帧 | 屏幕录像中，标题栏位置既没有原窗口、也没有卷帘条的帧 |
| 录屏指示器 | macOS 在被屏幕录制的窗口的关闭、最小化、全屏按钮位置绘制的紫色标记 |
| 恢复记录 | 收起时写入磁盘的记录，用于在 WindowShade 异常退出后恢复原窗口 |

## 2. 现有代码的问题

| 问题 | 事实 | 后果 |
|---|---|---|
| 状态集中在一个对象中 | `AppDelegate` 有 106 个成员变量，22 个源文件以扩展的形式向它添加方法 | 任何文件都可以修改任何状态，修改一处时无法确定影响范围 |
| 收起流程集中在一个函数中 | `ShadeController.shade()` 共 514 行，内部嵌套一个安装闭包，包含截图、裁剪、写恢复记录、移开原窗口、转移焦点、显示卷帘条 | 各步骤的先后顺序只由代码注释说明，没有测试检查。2026 年 10 月录屏中出现的空帧，原因是卷帘条显示晚于原窗口移开 |
| 主线程同步等待其他应用程序 | 收起过程中，主线程直接调用辅助功能接口读取访达的标题栏信息，一次等待 642 毫秒（2026-10-08 CI 日志） | 其他应用程序响应慢时，WindowShade 的界面停止响应 |
| 异常处理分散 | 截图有 3 种方式，移开原窗口有 5 种方式，另有桌面归属修正、定时核对、延迟验证重试等机制，分布在 `ShadeController.swift`、`FoldTransaction.swift`、`FoldExit.swift`、`OverlayPresentation.swift`、`Reconcile.swift`、`FoldCallbackGuard.swift` 中 | 无法从任何一处看出收起共有哪几步、每一步如何失败 |
| 应用程序判断分散 | `Compatibility/Policies.swift` 定义了 10 种应用程序的规则，另有约 40 处按 bundle ID 或应用程序名称判断的代码分布在其他文件中 | 新增或修改一个应用程序的处理方式时，需要查找多个文件 |
| 代码量分布 | 约 21,600 行 Swift 代码中，应用内更新占 3,811 行，收起与展开占 3,211 行 | 维护成本主要花在非核心功能上 |

## 3. 功能需求

优先级：P0 为必须实现；P1 为保留，可在 P0 之后改写；P2 为建议删除，由项目负责人决定。

### 3.1 收起与展开（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1 | 用户双击任意窗口的标题栏，或按 `⌃⌘C`，该窗口收起 | 从双击到原窗口主体从屏幕上消失，不超过 250 毫秒；录像中没有空帧；收起过程中其他窗口不覆盖卷帘条 |
| F2 | 用户双击卷帘条、按 `⌃⌘C`、按 `⌃⌘1` 至 `⌃⌘9`，或在菜单中选择该窗口，该窗口展开，并成为当前窗口 | 展开后的位置和大小与收起前相同；录像中没有空帧 |
| F3 | 收起和展开时不出现系统的最小化动画 | 录像中没有窗口缩入程序坞的过程 |
| F4 | 收起后，键盘焦点转到原窗口后方的窗口，菜单栏显示该窗口所属的应用程序 | 收起后的按键输入不发送到原窗口 |
| F5 | 用户三击标题栏时，执行系统设置中“双击窗口标题栏”所指定的操作（缩放或最小化） | 与系统设置一致 |

### 3.2 卷帘条（P0）

| 编号 | 需求 |
|---|---|
| S1 | 卷帘条显示原窗口标题栏的截图，位置与原标题栏重合，圆角半径与原窗口相同 |
| S2 | 用户可以拖动卷帘条；展开时原窗口出现在卷帘条的新位置 |
| S3 | 卷帘条上的关闭、最小化、全屏按钮作用于原窗口；关闭有未保存内容的窗口时，原应用程序的“是否保存”对话框照常出现 |
| S4 | 卷帘条为当前窗口时，`⌘W`、`⌘M`、`⌘H`、`⌘Q`、`⌘N` 发送给原窗口所属的应用程序；`⌘Q` 发送前先展开原窗口 |
| S5 | 没有屏幕录制权限，或截图检查不通过时，卷帘条改为显示统一样式的标题栏 |

### 3.3 看一眼（P0）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| G1 | 指针在卷帘条上停留 0.25 秒后，卷帘条下方显示画面卡片，尺寸与原窗口相同；指针移开后画面卡片关闭 | 指针经过卷帘条但停留不足 0.25 秒时，不显示画面卡片；按住鼠标或拖动卷帘条时不显示画面卡片 |
| G2 | 画面卡片优先显示实时画面；无法获取实时画面时显示收起时的截图。卡片上不加任何文字说明 | — |
| G3 | 用户单击画面卡片或双击卷帘条时，原窗口展开；画面卡片在原窗口回到原位之后才关闭 | 录像中没有空帧，没有录屏指示器 |
| G4 | 显示画面卡片时，当前应用程序不变，任何窗口的位置不变 | — |

### 3.4 收起后的外观（P1）

| 编号 | 需求 |
|---|---|
| A1 | 三种外观可选：原标题栏截图、统一样式的标题栏、缩略图 |
| A2 | 卷帘条透明度可调；可设置卷帘条始终显示在其他窗口上方 |
| A3 | 收起和展开时可播放音效，两个音效分别可选 |
| A4 | 按 `⌃⌘0` 时，所有卷帘条排成一列；再按一次，卷帘条回到原位置。外观为缩略图时，缩略图排列在屏幕底部 |

### 3.5 菜单栏与设置（P1）

| 编号 | 需求 |
|---|---|
| M1 | 菜单栏菜单包含：收起或展开当前窗口、已收起的窗口列表（前 9 项对应 `⌃⌘1` 至 `⌃⌘9`）、全部展开、设置、退出 |
| M2 | 设置窗口包含四页：卷帘、快捷键、权限与启动、高级 |
| M3 | 每个快捷键可以重新录制或清除。新安装时不设置任何快捷键；从 1.0.15 及更早版本升级时保留原有快捷键 |
| M4 | 首次打开时显示欢迎窗口，引导授予两项权限 |

### 3.6 可靠性（P0）

| 编号 | 需求 |
|---|---|
| R1 | WindowShade 崩溃、被强制退出或电脑断电后，下次启动时恢复所有处于收起状态的原窗口 |
| R2 | 用户通过程序坞、`⌘Tab` 或调度中心使原窗口重新显示时，WindowShade 移除对应的卷帘条 |
| R3 | 原窗口关闭或其所属应用程序退出时，WindowShade 移除对应的卷帘条 |
| R4 | 切换桌面或接入、断开显示器后，卷帘条仍位于原窗口所在的桌面和显示器上，且全部位于屏幕可见范围内 |
| R5 | 主线程不同步调用任何其他应用程序的接口。其他应用程序无响应时，WindowShade 的菜单和卷帘条仍能响应操作 |
| R6 | WindowShade 不合成任何鼠标或键盘事件，不移动光标；操作其他应用程序的窗口只用辅助功能。全局鼠标钩子在 0.4 秒内放行每一个事件，任何其他应用程序无响应、WindowShade 自己停住时，系统的输入都不受影响（钩子在单独的进程里，第 5.9 节）。卷帘条上的按钮转给原窗口时每个动作至多执行一次 |

### 3.7 删除的功能（2026-10-08 决定）

| 功能 | 删除理由 | 状态 |
|---|---|---|
| 专注当前应用程序（外观为统一样式的标题栏时，`⌃⌘0` 的另一种行为） | 与收起单个窗口无关；`App/FocusSession.swift`（563 行）全部用于此功能，`App/ArrangeController.swift` 中的专注排列部分也用于此功能 | 已删除；`⌃⌘0` 在所有外观下都整理卷帘条 |
| 应用内更新的看护进程、更新前备份、失败后恢复旧版本 | 约 3,000 行；改用 Sparkle 的标准更新流程（下载、校验签名、替换、重新启动） | 已删除；同时删除欢迎窗口中“移到‘应用程序’文件夹”一步，Sparkle 在不可写的位置会提示用户自行移动 |
| 关闭“看一眼”后，单击卷帘条显示的小缩略图 | 功能与“看一眼”重复 | 已删除；关闭“看一眼”后单击卷帘条不再弹出内容，菜单悬停预览保留 |

## 4. macOS 的限制

下表列出影响设计的系统限制，以及本设计对每项限制的处理方式。

| 限制 | 处理方式 |
|---|---|
| 无法可靠地把其他应用程序的窗口缩小到只剩标题栏的高度 | 收起时把原窗口移开，在原位置显示标题栏截图 |
| 系统不允许其他应用程序的窗口完全移出屏幕，窗口至少保留数个像素在屏幕内 | 原窗口移到屏幕右下角（右下角与其他显示器相邻时改用左下角），只保留 1 像素在屏幕内（`Core/CornerParking.swift`） |
| 系统完整性保护开启时，跨进程调用 SkyLight 私有接口修改窗口位置或透明度，调用返回成功，但窗口不变 | 第一次检测到无效后，把结果与系统版本一起写入用户偏好；系统版本不变时不再调用 |
| 最小化必然播放缩入程序坞的动画 | 最小化只在其他方式全部失败时使用 |
| 隐藏整个应用程序时，系统会同时切换当前应用程序，并可能切换桌面 | 只在原窗口是该应用程序唯一的窗口、且当前桌面上有其他窗口可以接收焦点时使用 |
| 截图需要屏幕录制权限；用 ScreenCaptureKit 持续采集某个窗口时，系统在该窗口上绘制录屏指示器 | 没有权限时使用统一样式的标题栏；原窗口重新显示之前，先停止采集 |
| 辅助功能接口是同步的跨进程调用，对方无响应时调用方一直等待，直到超时（WindowShade 设定为 2 秒） | 所有辅助功能调用在后台队列执行 |
| WindowShade 显示的窗口，要等主线程当前这一轮运行循环结束后才出现在屏幕上；其他应用程序移动自己的窗口则立即生效 | 显示卷帘条后立即绘制并提交，等待 2 帧，再移开原窗口 |
| 进程启动后第一次调用窗口截图接口，耗时可达 700 毫秒 | 启动 1 秒后在后台截取 1 像素，使第一次收起时不再承担这部分耗时 |

## 5. 架构

### 5.1 分层

```text
应用层    AppDelegate、菜单栏、设置窗口、欢迎窗口
功能层    FoldEngine、UnfoldEngine、Glance、Thumbnail、Arrange
领域层    ShadeStore、ShadeRecord、FoldPlanner、AppProfiles、Journal
平台层    Accessibility、WindowServer、Capture、Stream、SkyLight、Spaces
```

各层的规定：

1. 只有平台层调用系统接口（辅助功能接口、CGWindow、ScreenCaptureKit、SkyLight）。其他层从平台层得到的是数值类型（`WindowFacts`、`CGImage`、成功或失败），不持有 `AXUIElement`。
2. 领域层不依赖 AppKit，不读取当前时间，不创建线程。时间由调用方作为参数传入。领域层的全部判断都能在单元测试中执行。
3. 所有收起状态只保存在 `ShadeStore` 中，只能通过 `ShadeStore` 的方法修改。菜单、看一眼、卷帘条排列订阅 `ShadeStore` 的变化通知，不另存副本。
4. `AppDelegate` 不保存状态，只在启动时创建并连接各模块。
5. 平台层的每个模块对外提供一个 Swift 协议，例如 `AccessibilityClient`、`WindowCapturing`、`WindowMoving`。`FoldEngine`、`UnfoldEngine` 和 `Glance` 只依赖这些协议，不直接引用平台层的具体类型。单元测试和组件测试用模拟实现代替真实的系统调用（见 [`testing.md`](testing.md) 第 2 节）。

### 5.2 收起记录

每个处于收起状态的窗口对应一条记录：

```swift
struct ShadeRecord {
    let windowID: CGWindowID
    let pid: pid_t
    let appProfile: AppProfile.ID
    var frame: CGRect              // 展开时的目标位置和大小；拖动卷帘条时更新
    var space: SpaceID?            // 原窗口所在的桌面
    var display: DisplayID?        // 原窗口所在的显示器
    var look: Look                 // .screenshot、.titleBar、.thumbnail
    var hiddenBy: HideMethod       // .appHidden、.cornerParked、.skyLightOffscreen、.minimized
    var phase: Phase               // .folding、.folded、.unfolding；不允许的状态转换直接拒绝
    var transaction: UUID          // 异步回调返回时用于核对，不一致的回调丢弃
}
```

现有代码中分别保存在 `ShadeState`、`foldWaiters`、`foldWaiterTransactions`、`restoreVerificationTokens`、`arrangedOverlayFrames`、`hoverPreviewSuppressedUntil` 等字典中的数据，全部并入这条记录或 `ShadeStore` 的方法。

### 5.3 应用程序配置表

所有针对特定应用程序的处理方式写在一张配置表中：

```swift
struct AppProfile {
    let id: ID
    let match: [Match]              // 优先按 bundle ID 匹配，其次按应用程序名称
    let hideOrder: [HideMethod]     // 移开原窗口的方式，按顺序尝试
    let allowAppHide: Bool          // 是否允许隐藏整个应用程序
    let chromeHeight: ChromeRule    // 标题栏高度的取得方式：.accessibility、.standard、.fixed(51.5)、.scanPixels
    let nativeShade: Bool           // 是否使用系统自带的收起功能（便笺）
    let stripResizable: Bool        // 卷帘条是否允许拉宽
    let note: String                // 采用此配置的原因和对应的实测记录
}
```

- `Compatibility/Policies.swift` 中的 10 种应用程序，以及其他文件中约 40 处按应用程序判断的代码，全部改为配置表中的条目。收起、截图、标题栏识别的代码中不再出现 bundle ID。
- 新增一个应用程序的配置，需要两项改动：在配置表中增加一条，在录像测试中增加该应用程序（见 `testing.md` 第 4 节）。
- 未列入配置表的应用程序使用默认配置：标题栏高度先从辅助功能接口读取，读取结果不可信时分析截图像素；移开原窗口的顺序为隐藏整个应用程序（满足第 4 节的条件时）、移到屏幕角落、最小化。

### 5.4 收起流程

`FoldPlanner` 是纯函数，输入为窗口信息、应用程序配置和用户设置，输出为收起计划。`FoldEngine` 按计划依次执行以下步骤，记录每一步的耗时。

| 步骤 | 内容 | 执行线程 | 时间上限 | 失败时的处理 |
|---|---|---|---|---|
| 1 | 确定双击位置所在的窗口和标题栏 | 后台 | 30 毫秒 | 不收起 |
| 2 | 读取窗口位置、大小、标题栏高度、所属应用程序的窗口数量、所在桌面 | 后台 | 40 毫秒 | 读取失败的项使用默认值 |
| 3 | 生成收起计划 | 后台 | 1 毫秒 | — |
| 4 | 截取原窗口并裁出标题栏 | 后台 | 80 毫秒 | 改用统一样式的标题栏 |
| 5 | 把恢复记录写入磁盘 | 后台 | 10 毫秒 | 不收起，提示用户一次 |
| 6 | 显示卷帘条，立即绘制并提交，等待 2 帧 | 主线程 | 40 毫秒 | — |
| 7 | 按计划的顺序移开原窗口 | 后台 | 60 毫秒 | 尝试下一种方式；全部失败时移除卷帘条，删除恢复记录 |
| 8 | 把键盘焦点转给原窗口后方的窗口；此步骤执行期间，卷帘条的窗口层级临时提高一级 | 后台 | 40 毫秒 | 不转移焦点 |
| 9 | 播放音效，更新菜单，为卷帘条启用看一眼 | 主线程 | 不计入 | — |

- 从双击到原窗口主体消失的时间为步骤 1 至步骤 7 之和，上限约 260 毫秒。2026-10-08 的 CI 录像中，实测值为 459 毫秒至 2,277 毫秒。
- 步骤 6 必须在步骤 7 之前完成，步骤 8 必须在步骤 6 之后开始。这两项顺序由 `FoldPlanner` 的输出表示，并由单元测试检查。
- 步骤 7 之后，在后台检查原窗口是否已离开屏幕。检查不通过时，按 `hideOrder` 尝试下一种方式，卷帘条位置不变。

### 5.5 展开流程

| 步骤 | 内容 |
|---|---|
| 1 | 如果画面卡片正在显示实时画面，停止采集；画面卡片保留最后一帧 |
| 2 | 把原窗口移回收起记录中的位置和大小 |
| 3 | 检查原窗口已出现在屏幕上，位置与记录一致 |
| 4 | 在同一帧中关闭画面卡片和卷帘条 |
| 5 | 把键盘焦点交给原窗口 |
| 6 | 删除恢复记录 |

### 5.6 定时检查

存在收起的窗口时，每秒检查一次，只处理两种情况：

- 原窗口已经回到屏幕上（例如用户通过程序坞或 `⌘Tab` 使其重新显示）：移除卷帘条，删除恢复记录（对应 R2）。
- 原窗口已不存在（窗口关闭或应用程序退出）：移除卷帘条，删除恢复记录（对应 R3）。

桌面切换和显示器变化改为响应系统通知处理，不在定时检查中处理。

### 5.7 恢复记录

- 在移开原窗口之前写入磁盘（收起流程步骤 5），在展开流程步骤 3 的检查通过之后删除。
- WindowShade 启动时，首先读取恢复记录，把记录中仍未显示的原窗口全部移回原位置（对应 R1）。
- 记录格式与现有 `Recovery/Journal.swift` 兼容，用户升级后不丢失收起的窗口。

### 5.8 线程

- 主线程只执行 AppKit 操作：创建窗口、修改窗口层级、绘制卷帘条、更新菜单。
- 辅助功能调用、窗口截图和像素分析在后台队列执行。对同一个应用程序的辅助功能调用依次执行，对不同应用程序的调用互不等待（保留现有的 `Core/AXReadGate.swift`）。
- 主线程单次阻塞超过 16 毫秒时写一行日志（保留现有的主线程阻塞监测）。
- 全系统的鼠标钩子不在 WindowShade 进程里，见第 5.9 节。

### 5.9 鼠标钩子进程

双击标题栏收起要吞掉那次双击，否则系统同时执行自己的双击动作（缩放或最小化）。能吞掉事件的钩子是主动钩子：钩子回调返回之前，全系统后续的点击都在等它。钩子放在 WindowShade 进程里时，WindowShade 整个进程停住（崩溃时系统生成报告会先把它挂起，调试器暂停），全系统的点击要等系统约 2 秒后停用钩子才放行（CI 场景 X11 实测 2.0 至 2.3 秒）。2026-10-08 用户遇到的情况是指针能移动、触控板手势有效，点击和快捷键一直没有反应，只能强制重启。

钩子因此放在一个只做这件事的小进程 `WindowShadeTapHelper` 里（`prototype/TapHelper/main.swift`，放在 `Contents/MacOS/`）：

| 项目 | 规定 |
|---|---|
| 单击 | 直接放行，不问 WindowShade |
| 双击、三击 | 经 `CFMessagePort` 问 WindowShade 要不要吞掉；送出最多等 0.1 秒（只在 WindowShade 积了很多询问时才会等），等回话最多 0.4 秒（`Core/TapProtocol.swift`）；没有回话、出错一律放行 |
| 吞掉一次按下 | 同时吞掉与它配对的松开（macOS 26 起系统在第二次松开时执行双击缩放） |
| 不做的事 | 不显示界面，不调用辅助功能接口，不读写文件，回调里不等待任何没有时限的东西 |
| 生命周期 | WindowShade 有辅助功能权限后启动它；WindowShade 退出（包括崩溃、被强制结束）时它随即退出 |
| 意外退出 | WindowShade 0.5 秒后重新启动它；一分钟内退出 3 次，改用 WindowShade 自己的钩子 |
| 建不了钩子 | 以退出码 2 退出，WindowShade 改用自己的钩子（第 5.8 节旧做法：钩子在独立线程上，问主线程最多等 0.4 秒） |
| 日志 | 写到标准输出，WindowShade 加上 `tap-helper:` 前缀写进自己的日志；输出不阻塞，管道满时丢弃 |

WindowShade 处理询问时先看询问发出的时刻：距今超过 0.35 秒的不处理（钩子已经放行，再收起，用户会同时看到系统的双击动作和收起）。

钩子进程由 WindowShade 启动，辅助功能授权按启动它的 WindowShade 计算，不需要用户另外授权。CI 场景 X11（WindowShade 停住 3 秒）、X12（钩子进程被强制结束）检查这一节。

## 7. 测试

测试的内容、方法、需求与测试的对照、端到端场景、缺陷回归记录和录像检查的判定方法，见 [`testing.md`](testing.md)。

本设计对测试的要求：

1. 每条功能需求至少对应一项自动化测试。
2. 修复缺陷时，先编写能复现该缺陷的测试并确认其失败，再修改代码。
3. 是否通过由自动检查判定，不以人工观看录像作为依据。

## 8. 改写顺序
