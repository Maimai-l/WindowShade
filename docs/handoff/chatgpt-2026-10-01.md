# ChatGPT 交接规格 v2–v4 要点（2026-10-01）

来源：Aaron 分享的 ChatGPT 会话 <https://chatgpt.com/share/6abe228f-ab88-83ec-ad07-9d773072cf8a>（“研究整合 CarPlay 接收器”），
2026-10-03 由 Claude 从头读到尾，包括会话里的附件：v2 电量与灵动岛增补规格、v3 遥控器与语音编程规格、v4 身份认证与 MFA 主规格、
论文研究笔记，以及三份“给执行模型的开场指令”（START-HERE-v2/v3/v4）。交接包里的验收 JSON 没有随分享页公开。

这些是 Aaron 定下的产品目标，不是支线。每份规格都强调同一件事：**不能把一个演示、一段动画或一组模拟测试当作整条链路做完**。

## v2：设备电量与完整灵动岛（在 CarPlay 接收的规格之上）

- **目标**：连接或配对成功时显示那台设备的真实电量；键盘、鼠标、触控板、AirPods（左耳、右耳、盒分开）、iPhone、Apple Watch、
  Vision Pro、本机 Mac 低电量时，在同一处可展开、可交互的灵动岛里提醒。不是电量菜单栏小工具，也不是一个黑色通知条。
- **灵动岛完整交互**：紧凑、最小、展开、短暂提醒、持续活动、多个活动的打断与恢复、主动收起、隐私抑制（锁定、切用户时清掉）、
  无刘海屏用胶囊、减少动态效果、VoiceOver、键盘。活动的状态来自数据，不能由动画回调决定。
- **数据规则**：按稳定设备 ID 和组件 ID 管理，名称只作展示；“最后看见设备”“最后读到电量”“来源采样时间”分开；
  没读到就是未知，合法的 0% 才是零；充电状态没有可靠字段就是未知。低电量 20% / 10% / 5% 三档，同一放电周期每档只提醒一次，
  回滞 5 个百分点，断开重连、重启不重播。耳机按最低的一侧提醒，不取平均。
- **事件分清**：附近广播只算发现；启动时枚举到的历史配对不重播“已配对”；经 iPhone 读到的手表电量写“来自 iPhone”。
- **AirBattery（AGPLv3）只作研究来源**，不能复制核心代码改名进 MIT 主项目。它的 12 处问题（按名称合并、普通 Bool 当锁、
  旧电量被连接心跳续期、未知变 0、把电量上涨当充电……）要修正，不继承。
- **顺序**：B0 基线核对 → B1 纯逻辑模型 → B2 第一个真实闭环（本机电池或一件妙控外设）→ B3 完整交互与多活动 →
  B4 iPhone / iPad / Watch / Vision Pro → B5 与 CarPlay 汇合 → B6 恢复、能耗、发布审查。附 64 个未执行的验收场景。
- **性能**：电量采集不进绘制、动画或全局输入回调；事件驱动为主、低频刷新补足；动效结束即停止刷新，待机没有 display-link。

## v3：遥控器指挥与语音编程

- **目标**：iPhone 控制中心的 Apple TV 软件遥控器（参考 corvofeng/atv-core）变成 vibe coding 工具。触控区不当光标，
  像指挥家一样：**声调**一声 → low、二声 ↗ medium、三声 ˇ high、四声 ↘ xhigh；**拍子**一至四同上，max 只来自完整五拍（3+2），
  ultra 只来自完整六拍（3+3）。整句结束才判定，五拍的前四拍不先切到 xhigh。按住说话出可检查的草稿，独立提交才发出去。
  每一步都在刘海上有清楚、即时的反馈（轨迹与拍点、候选档位、目标会话、真实录音、草稿、配置回执、运行与审批）。
- **按钮**：TV/Home 短按切“模型 / effort”选择域，长按选项目和会话；Select 确认；Siri 按住录音；Play/Pause 提交或请求中断；
  Back 取消。音量键不用来调档。
- **必须先修**：atv-core 的 pair_verify_m3 没验证客户端签名就发 Verified，不能当授权；Idle 模式要有独立的原始触摸接口；
  轨迹要保留全程，不只看起终点；按钮要有按下、松开、取消三个阶段。
- **后端如实**：按 Codex App Server 的 model/list 和 Claude 的实际能力生成选项；Claude 的 ultracode 是 xhigh 加工作流程，
  不是 max 之上的 effort；不支持的档位明说不可用，不默默降档。遥控器控制的是具体项目、会话、轮次，不往前台窗口盲发回车。
- **连续互通麦克风**：同一台 iPhone 同时当遥控器和麦克风能否共存，第一批就要实验。
- **顺序**：C0–C6，先在没有执行能力的测试面板验证输入和身份，再接一个真实后端的只读任务。附 64 个未执行的验收场景。

## v4：身份认证、MFA、在场保护与真正解锁

- **整体目标保留**：掀盖或唤醒时的安全呈现 → 真实身份验证 → 多设备确认 → 绑定具体操作的授权 → 真正解锁 macOS → 新鲜桌面交接；
  离位与防盗；刘海和无刘海胶囊里的认证交互。CarPlay、电量、灵动岛、指挥模式都继续。
- **授权的不变量**：只消费验证器自己发出、仍有效、用途和目标完全一致的一次性请求（purpose、targetDigest、nonce、epoch、
  撤销、原子消费）。连接状态、设备名称、UI 上的“已验证”、动画对勾、手势候选、健康数据都不能产生授权。
- **因素要算对**：人脸加指纹是两种生物模态，不自动等于两个因素；设备私钥的持有加系统生物识别激活才是多因素认证器候选。
- **研究结论（会改变做法的）**：心率、脸红判断不了诚实或主人（国家研究委员会测谎报告）；Apple 开发者协议对 Face Data 用于认证、
  对 HealthKit 数据的用途都有限制，先审查再用；NIST SP 800-63B-4 排除声纹比较，生产基线不让声纹授权（语音输入照做）。
  AWDL 论文不能当“天然省电”的证明；PrivateDrop 的亚秒延迟是 USB 条件下测的。
- **真正解锁**：本应用确认、受保护资源、agent 动作、macOS 会话解锁、FileVault 预启动分别验收；后端没核实前不存登录密码、
  不模拟输入凑一个“成功”。
- **顺序**：A0 现状与用途审查 → A1 原子交易与本机原生认证闭环 → A2 手机设备证明与恢复 → A3 面容 / 注视 / 防伪研究 →
  A4 真正系统解锁后端 → A5 离位、防盗与资源联合 → A6 独立攻防与发布资格。附 96 个未执行的验收场景。

## Aaron 之后的改动（2026-10-03）

- 不走 App Store 分发：Face Data 用途限制不作门槛，私有 API 能达成目的就用。
- 声纹作多因素认证的辅助因素（不单独放行），推翻 v4“声纹不产生授权”。
- CarPlay 是全屏体验：长按刘海进入，短按刘海仍是启动台。
- 详见 [direction.md](../direction.md)“刷脸解锁：吸收 Glance”和 [blueprint.md](../blueprint.md)。
