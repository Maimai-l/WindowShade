# 第九份：修复旧窗口路径，不再把未知当成功

直接使用统一 v9 的 `candidate-repo/`。本份精确基线为 v8 的 1164 个文件，不是公开仓库当前 HEAD。已有更新的工作区按 `base-sources/`、`overlay/` 和 manifest 三方合并；不要覆盖用户改动，不要重复叠前八份。

本份已经修复实际的 FoldCompletion、FoldTransaction、ShadeController、Reconcile 和 AX 回调路径，并修复 EffectFrameAwaiter 的严格 Swift 6 隔离问题。它没有新建平行窗口管理器，也没有把这些实际代码再留作下一份设计任务。先运行 README 的命令，再做完整 Mac 构建；不要降低 Swift 版本、屏蔽并发错误或删掉 Sparkle 来获得通过。

## 本次已经定下并写入的行为

收起结果分成 hidden、visible、unknown。缺失 AX 属性、类型不对、窗口身份不符或系统锁态未知，都不能报告隐藏成功。一般窗口不以离开当前 on-screen 列表作为隐藏证明。未知时不换另一种方法继续修改窗口，保留原恢复记录和人工恢复入口。

完成通知绑定具体 transaction 和捕获的 waiter tokens，先从账中整批取出，再排队通知。通知真正执行前还要重查当前事务、启动与锁态代次、显示上下文和有效期。布尔 false 包含未知、过期、取消，绝不等于窗口没有被修改或已经恢复。

后台巡检的结果随窗口、进程、事务、隐藏方法、boot、sessionEpoch、presentation 和采样时刻返回；旧结果不能清理新状态。AX observer 使用本次注册的单调 routeID，不能再拿 windowID 直接路由。通知只是核查提示，不直接兑换恢复或授权。

首帧等待显式继承调用者隔离；读取到帧后还会重查取消、捕获代次和期限。不要给帧对象随意加 Sendable 或将所有调用硬搬到 MainActor。

## 执行顺序

1. 在统一候选运行新 regression/frame 和旧 duo、part8 input/fold/flow。每套分别留命令与输出。第七份和更早回归命令也在 README。
2. Mac 上执行隔离的 `tests/run-mac-check.sh`。本轮 Linux 未取得 SDK，纯逻辑通过不能替代这个步骤。先修实际错误，再观察窗口。
3. 按工单 02 验证原收起、手动恢复、连续重收、切换 Space、权限丢失和锁屏。unknown 时恢复入口必须仍在，不能为了界面干净直接删除 journal。
4. 按工单 03 检验浏览器完成通知、首帧和慢窗口。原生 resize 不再通过嵌套 RunLoop 等待；较慢应用可能更常走已有 proxy fallback，需要真实对照。

完整 T3 自动恢复、配对接收、原生允许审批和系统身份后端没有因此完成。剩余的实际代码与证据分列在 REMAINING。保留默认只读助手，不改批准策略，不启用自动窗口效果，不改版本、更新源或签名身份。

# 第九份变更

基线 v8，1164 文件；结果 v9，1168 文件。11 处替换、4 处新增，没有删除。以 manifest 的逐文件 SHA256 为准。

## 实际源码变化

增加两个小型现有路径适配文件：Core/WS2FoldCallbackStamp.swift 保存瞬时回调身份与严格 CFBoolean 判断；App/WS2FoldCallbackGuard.swift 将这些规则接到实际锁态、窗口观察、observer 和恢复提示。没有新建第二套窗口状态或 journal。

FoldCompletion 从按窗口批量通知改为事务绑定、整批取出、排队和成功投递复核。ShadeController 在原生/代理两条安装路径绑定本次 token，把 admission 复核扩展到普通窗口实际隐藏前，并移除安装中嵌套 RunLoop 等待。

FoldVerifier 引入 hidden/visible/unknown；旧 Bool initializer 为原 standalone 客户与测试保留，但生产调用改用 typed 初始化且没有 screen-absence quick shortcut。FoldTransaction 统一真实观察、限制同策略最小化重试、保存 unknown 的人工恢复入口。

AX observer 的 refcon 改为本次注册路由；移除先撤路由，旧通知排队后再次核查。Reconcile 每应用产生不可变快照，按批次与事务代次应用；活应用的多次 AX 失败不再仅凭计数清理原生状态。WindowShade.swift 增加相关账与上下文字段，删除不再使用的旧巡检工作队列字段。

EffectFrameAwaiter 使用调用者隔离并验证取帧后的取消、期限与捕获代次。WindowBrowserAppDelegate 只修正完成回调契约注释。tests/duo-integration-check.py 更新为显式 transaction 调用并增加绑定断言；原 Swift DuoCoreTests 不改。

## 集成与兼容注意

完成通知从同步改为主队列异步。false 可能是未知或过期，不等于未发生副作用；客户不能默认重试。即使已准备成功，投递前换代也会降为 false。

unknown 不再跨隐藏策略追加副作用，保留恢复入口。原生 resize 不再嵌套运行循环，较慢应用可能更常使用已有 proxy fallback。实际效果、焦点、Space、锁态与 AX 类型均需 Mac 回归。

完整 T3 自动恢复没有开放；原只读助手与手柄确认边界不变；没有新视频、真实账号、配对、签名或发布。

# 01　这次具体修了什么

事实依据是 v8 候选与本份差异、实际测试日志和源码索引。下面的源码结论不等于已经在 Mac 看见对应故障；没有硬件复现的地方明确保留层级。

## 两个旧完成通知问题已经复现

`tests/reproduce-v8.py` 从精确 v8 读取原 FoldCompletion，只将 Cocoa import 换成 Foundation，并补入它所需的字段宿主。它实际编译并运行原函数，没有用另写的近似函数替代旧行为。

第一个场景：窗口 W 上旧请求 A 注册等待，随后新请求 B 也注册；旧路径按 windowID 批量发成功，B 同样收到成功。这说明当时的等待账不能区分结果属于哪次收起，不能据此声称真实 Mac 窗口已经错误收起。修复是绑定 A、B 各自的 transaction，只结算该事务捕获的 token。

第二个场景：一批成功通知里，第一个回调同步取消第二个等待者。原函数尚未取出第二个回调，它就会被取消分支先取走并收到 false。修复先取出整批再通知；没有依赖字典迭代的固定顺序。回调虽然晚些执行，但其成功仍要通过届时的上下文复核。

基线复现日志在 `validation/baseline-reproduction.json`。这是两项旧缺陷复现，不是新增两项“修复测试”，也不是两次 AX 真机操作。

## 源码核对发现的误判与竞态

|位置|旧路径的具体风险|本份修复|证据层级|
|---|---|---|---|
|hideTookEffect|部分方法把 AX 几何缺失、应用对象缺失当成功|统一通过 typed observation，只有 hidden 才为 true|源码差异；类型转换与 reducer 测试；Mac 未运行|

|FoldCompletion|只按 windowID 结算，客户回调在账尚未处理完时重入|事务绑定、整批取出、排队、投递前复核|旧函数复现及实际新文件的测试宿主|

## 修复没有偷换问题

没有用重新生成 UUID 来掩盖原窗口仍在屏幕外；新的 stamp 只用于拒绝旧回调。没有因 AX 连续失败三次就删除仍活着的应用的恢复状态。没有把“保留人工恢复入口”写成“自动恢复成功”。也没有把源码文本检查写成 SDK 编译或实际窗口验证。

旧完成 API 的调用者还只接收 Bool。本份通过注释与文案收紧了含义，但没有一次性改掉全产品所有返回类型。调用者不能因 false 自动重试收起，也不能因一次 true 获得未来任意时刻恢复该窗口的权利。

# 02　窗口验证与未知状态

这些是本项目的实现规则。真实 AX、AppKit 和私有窗口行为还需 Mac 验证；没有把规则当作已测量的平台保证。

## 每种隐藏方法读自己的证据

`observeFoldHide` 先检查系统已解锁，再按方法读取当前事实。普通远端窗口还需当前应用存在且未退出、AX 对象的 windowID 和 PID 与记录一致。

|当前隐藏方法|可接受的当前观察|未知时怎么办|
|---|---|---|
|offscreen / privateOffscreen|新读取的位置、尺寸均有限且尺寸为正，再按现有屏幕几何判断|保留恢复，不以读不到坐标当已移走|
|hidden|当前 NSRunningApplication 的真实 isHidden|应用对象缺失不能替代隐藏证据|
|minimized|AX 调用成功且值是真正 CFBoolean|nil、数字 0/1、字符串或读失败均 unknown|
|privateAlpha|当前读回 alpha 有限且在 0…1，按既有阈值判断|读回失败不默认 1 或 0|
|ownWindowOrderedOut|确实是本进程原生窗口，读其 isVisible|找不到该 NSWindow 为 unknown|
|quickLookClosed|针对被有意关闭窗口的 includingWindow 查询成功，返回空数组|查询失败或仍有条目为 unknown，不泛化为所有隐藏方法|
|none（原生缩高）|原来的 resize 验证单独处理|不能拿“不是隐藏”自动当成功|

CFBoolean 检查被抽成 `ws2ObservedBoolean`，实际跑了 CoreFoundation 类型测试。这个测试证明本轮函数不会把一般数字当布尔，不证明所有应用都会正确提供 AX 属性。

## 重读可以等待，不应重复制造不同副作用

第一次读回未确认后沿用既有延迟再读。第二次仍 unknown 就结束本次验证，保留恢复入口。若明确 visible，只有原隐藏方法已经是 minimized 才允许再次尝试同一最小化操作；操作前仍查窗口身份、当前事务和锁态。

旧逻辑可能先使用 offscreen，读回不明确时再最小化，而恢复记录仍只写 offscreen。这样恢复坐标并不必然解除后来增加的最小化。本份因此移除了跨策略补写。它是完整恢复事务尚未具备时的保守选择，不是声称所有应用不能混用两种方法。

现有 verifier 的调度仍是首次 0.15 秒、下一次再等 0.45 秒、同策略补写后再等 0.35 秒。没有把这些数值改成实时保证。Apple 的 Run Loop 指南说明 timer 投递可因运行循环忙碌而推迟，且可以发生嵌套运行循环；本项目据此不把“等够了”作为窗口完成证据。[S02](sources/SOURCES.md#s02)

## unknown 的用户界面和清理

unknown 的完成等待返回 false，临时证据继续显示未确认；原 journal 和 ShadeState 留在原恢复链。已有 overlay 符合 Space 规则且仍是当前事务时，可呈现人工恢复入口，提示“收起状态未确认，点击可尝试恢复窗口”。quiet notice 说明恢复入口仍在，但不保证用户点击就一定恢复成功。

明确 visible 仍沿原来的失败回滚路径处理；这条路径也须精确事务核对。未知不能进入成功动画。完成通知延迟到真正执行时已过期，即使早先曾确认 hidden，也只能返回 false。客户端需要核对当前状态，不能自动再收一次。

屏幕和 Space 改变会撤销旧 presentation stamp。这解决的是旧结果在新显示上下文里被采用的问题；它不是系统锁的证明，不代替权限账，也不保证系统外部窗口变化与本地核对之间不存在竞态。

# 03　回调归属与重入

## 一次收起的顺序

```text
本地调用者注册 waiter token
  → 本次 shade 请求捕获 token 集合及 admission 上下文
  → 读取/准备原窗口和已有恢复意图
  → 安装实际 ShadeState(transaction)
  → 仅将捕获且仍存活的 token 绑定该 transaction
  → 身份与上下文最终复核后执行原隐藏动作
  → typed observation 检查结果
  → 从对应事务的等待账整批取出回调
  → 主队列投递前再核对成功 stamp
  → 通知本地调用者
```

“先取出再通知”只解决账本的重入。还要防止取出以后、真正通知以前状态又改变，所以成功投递另外保存当时的 stamp。不能在投递前重新生成一个当前 stamp 冒充原来成功属于新上下文。已有 30 秒 waiter 超时只结算该 token；稍后执行时找不到 token 即无效果。

## 整批取出后也要逐个复核

回调 A 可能关闭页面、展开窗口或改变锁态。即使 A、B 最初一起准备成功，A 运行后 B 的成功也可能过时。因此新函数对每个回调分别检查当前 stamp。回调不再从已经换代的账里查找同编号的新请求。

测试将“账被取出”和“回调被投递”之间的切换确定地插入，不靠重复运行随机撞竞态。覆盖窗口重新安装、锁后再解锁、过期、弱所有者消失、重复 token、多个事务同窗、不同窗以及客户回调触发的撤销。

## stamp 的字段及边界

`WS2FoldCallbackStamp` 包含 window、pid、transaction、hide、boot、sessionEpoch、presentation、capturedAt。相等的路径或名字不足以匹配；钟倒退、非有限时间、恰好过期也拒绝。生产默认 maximumAge 为 2 秒，是拒绝陈旧观察的工程值，不是实际 AX 时延成绩。

这份 stamp 没有进程启动时间、跨重启窗口 generation、用户手动操作 revision，也没有持久 run/effect 归属。它不会调用 AuthorizationService.consume。它只能限制当前进程内的旧结果，不能兑换系统解锁、命令批准或 T3 的自动恢复权限。

## AX observer 为什么要另一个 routeID

windowID 是事件目标，不是订阅本身的身份。新 observer 建立时分配本进程内单调递增且不复用的整数 routeID，并将 routeID 关联到 pid、windowID、transaction。C 回调的 refcon 只携带这个整数，不当作可解引用的对象指针。

注册在主 CFRunLoop；C 回调检查主线程后才进入对应 MainActor 入口。停止 observer 时先删除路由再移除 source，已经排队的回调回来找不到原路由就拒绝。队列内只传 route、stamp 和 notification 名称，不传一个跨边界后再盲解引用的对象地址。

销毁、取消最小化、应用重新显示都是核查提示。应用侧还要重新读相应事实：实际包括该窗口的枚举、当前严格最小化属性、活着的应用 hidden 状态等。路由 stamp 的时间是本地接收时间，不是 AX 服务器生成事件的时间；不能声称仅靠时间戳知道一条事件何时发生。

## 移植时禁止的简化

不要恢复 `settleFoldWaiters(id:success:)` 的按窗批量成功入口。不要在清理函数内部直接调用客户完成回调。不要在 callback 前只查 `self != nil` 或 enabled=true。不要为了“确保能成功”把 maximumAge 设为无限，或者捕获失败后重新绑定旧 token。真正需要更长等待时，应生成新观察且仍维持原事务归属。

# 04　巡检并发与生命周期

## 原问题与新数据流

原巡检把窗口引用送到后台读取，再按窗口编号应用结果。后台工作可能很慢；读到结果时，该编号对应的 ShadeState 已经经历展开、重收或隐藏方式变化。结果本身看起来合法，但已经属于上一次请求。

新目标快照在派发前捕获 stamp。每个应用内串行读取窗口，应用之间分别完成；每个后台闭包只构造自己不可变的结果数组，再交主线程。没有共享的 snapshots 数组在多个闭包里 append，也不再用调用方的 NSLock 加 group.wait 拼一个结果。

主线程保存 reconcileBatchID 和剩余应用数，先验证批次，再验证每条 stamp。当前 on-screen 列表在应用结果时重读，不沿用后台读取之前的屏幕状态。准备清理旧条目或同步 journal 前再次验证 stamp；循环中遇到一个未知窗口不把它当成其他窗口可清理的理由。

## 本次没有消除所有 AX 停顿

一应用已返回时，它的结果现在可以先被处理，不必等另一应用的结果。但下一轮整体巡检仍需等当前各应用的回调收齐，已经发出的 AX 调用也没有被这次补丁变成可取消操作。一个卡住的应用仍可能延后后续轮次。本份没有把丢弃过时结果描述成终止后台调用。

进一步治理应先记录每个应用的真实 AX 耗时和被丢弃的代次，再考虑带配额的每应用读取端口；不可不停启动新一轮读来掩盖旧读未返回，否则会积累更多同步 IPC。当前不新增这个读取子系统，避免在没有 SDK 验证时再制造第二套状态。

## 未知几何不意味着窗口已经消失

位置和尺寸必须有限，尺寸大于零。最小化值必须是明确布尔。读取失败时保留原状态；同一活着应用的原生缩高窗口，即使多次拿不到 AX 几何，也不再只凭失败计数清理。真正的应用退出和旧事务撤销仍走原清理路径，不能永久保留所有垃圾条目。

sourceWindowLooksUserVisible 也改为没有应用状态或 alpha 时保守不认定可见；minimized 未采样时不默认 false。这里“暂不认定可见”不是断言它不可见，只是不据此删除恢复入口。

## 锁态、显示上下文与嵌套循环

锁态未知或已锁时不开始新的巡检恢复，晚到结果也拒绝。解锁并不复活旧 stamp。显示器布局或 Space 改变推进 presentation，让已有结果重新观察。

原生 resize 的安装中曾显式运行一小段嵌套 RunLoop。代码在这期间可能收到又一次收起、锁态或 observer 回调，外层却仍在安装第一份状态。本份去掉这段嵌套等待，使用即时读取与已有 proxy fallback。代价是部分慢应用可能更常落到 fallback，需真机对比，不能声称视觉路径完全不变。

## 外部副作用仍非原子事务

在本地最终检查之后，另一个应用或用户仍可能改变窗口。stamp 防止本进程误用已经知道过时的结果，并不把 AX 和 journal 变成单个原子操作。真实取消、超时、物理写入已经发生的情况仍需保留恢复核对。完整 T3 的持久恢复缺口列在工单 04，不通过这个巡检补丁宣称消失。

# 05　Swift 6 与首帧等待

## 实际编译失败，不是推测

运行原 `tests/DuoCoreTests.swift`，保持 `-swift-version 6 -strict-concurrency=complete -warnings-as-errors`，原 EffectFrameAwaiter 的泛型 async 边界发生 actor 隔离报错。错误原文保留在 `validation/development/duo-swift6-original-isolation.json`。

原辅助函数需要读取调用者拥有的 frame 和闭包，逻辑上没有要把它们送到另一个隔离域。修复采用 `isolation: isolated (any Actor)? = #isolation`。Swift 的 SE-0420 定义了用可选 isolated 参数及 #isolation 继承调用者隔离的能力，并说明这可以让同一隔离域内传递非 Sendable 值。[S01](sources/SOURCES.md#s01)

本份使用这一语言能力，不修改工程全局语言模式，也不将帧类改成 @unchecked Sendable。MainActor 调用、独立 actor 调用和非隔离调用分别有测试；每个非 Sendable frame 留在自己实际的隔离域，不把它从 Task 结果中跨域返回来伪装合法。

## 取到帧不意味着它仍可用

latest 闭包有可能在取值期间让当前捕获源失效，或让时间超过截止。因此函数在取到值后再次检查 task cancellation、isCurrent、有限时钟、不倒退以及严格小于 deadline。timeout<=0、NaN、infinity、deadline 溢出和大数相加不能推进期限都会直接拒绝。

pause 仍由调用者提供，测试使用受控暂停。这个函数不能保证一个不推进时间、也不真正让出的错误 pause 会正常结束。它也不改变实际 ScreenCaptureKit 的取帧签名和生命周期；周边 `EffectFrameSource` 仍需整应用 Mac 编译。

## 旧测试如何保留

原 Swift DuoCoreTests 没有改源码，新的候选直接通过其原有角度、弹簧、首帧、恢复时钟、超时/重试和 journal 场景。Python `duo-integration-check.py` 是文本级接线检查，其旧字面量 `completeFold(success: true)` 在增加 transaction 参数后必须更新。本份要求新的调用显式带 transaction，并增加原生等待绑定检查，没有把检查删掉或改成无条件成功。

开发时另有两项错误如实保留：完成通知弱引用的 optional.map 触发 Swift 6 闭包隔离错误，改成显式 if-let；新测试最初把非 Sendable frame 作为 Task 返回值，后来将测试改成在原域验证并只返回 Bool。这些记录不能和最终测试数量叠加。

# 工单 04　T3 仍需要什么，本次不冒领

第九份修的是原收起路径的事实与回调正确性。它没有把瞬时 FoldEvidence.Event 或 WS2FoldCallbackStamp 转成 Focus 恢复 Receipt，没有启用完整番茄钟自动窗口效果。

要真正补齐 T3，沿已有 FocusEffectPlan、FocusEffectExecutor 和原恢复 journal 做实际端口：用户明确选择范围；读取强窗口身份和用户操作 revision；记录 run/effect/transaction 与前态；持久 prepare 成功后才修改；实际结果确认后提交 receipt；超时或取消后的迟到成功进入补偿核对；恢复前再次比较身份、当前 revision 和本轮所有权。不能直接调用有切换语义的 tuckAll。

具体还缺的生产证据来源是进程启动身份、window generation、可验证的用户手动调整 revision，以及原 journal 的持久关联。本次 boot/session/presentation 只能判断当前上下文是否撤销，不能替代这些字段。不得将 PID 或 windowID 再包进 UUID 就宣称强身份已经具备。

unknown 不是未写入。准备记录之后写入可能已发生，应该保留待核对项；不能自动再隐藏一次。失败恢复不能通过先删 receipt 再尝试动作来换取干净列表。进程重启后的恢复也不能凭旧屏幕坐标重放，需实际对象核对。

在没有上述端口时保持只计时，保留现有 T3 不可用说明。用户还能使用普通卷帘条与人工恢复，但不宣传专注结束能可靠自动复原所有窗口。开发者应先完成工单 02 的原路径回归，再接新的自动效果，否则旧失败会被新的生命周期放大。
