# 06　本份之后怎样收尾

本份消除了已定位的错误返回和过期回调入口，也让原严格 Swift 测试重新能编译。接下来应拿这些候选去做真实 Mac 构建与窗口回归；不能以更多纯逻辑 helper 代替 SDK 结果。

## 三种状态必须分开

源码接线已经存在的部分：收起验证、事务等待账、AX route、后台巡检结果代次、首帧等待。平台证据尚缺的部分：AppKit/AX 类型检查、私有窗口方法、observer 线程、全应用 Metal/链接。产品目标仍缺生产代码的部分：完整 T3 恢复端口和持久归属、其他输入与配对装配、身份系统等。三者不能写成同一个“待实测”。

## 不借修 bug 偷改产品

继续使用原刘海宿主、恢复 journal 和 AuthorizationService。read-only 助手入口不因本次窗口修复放开 allow；手柄选模型不增加发送草稿或认证能力。没有新增后台网络监听、摄像头、麦克风、BLE 或人脸保存。新 route、stamp 和 batch 都只在内存存活。

## 适合接下来的合并单位

先把本份同一事务的字段、创建、绑定、使用、清理一起合并，不拆开导致有调用没有状态。然后验证原窗口功能和原浏览器完成回调。再验证慢应用、权限撤销、锁/睡眠、多屏和 Space。只有这些结果支持，才考虑开启完整 T3 的生产实现；T3 仍需用户操作 revision、run/effect 与原持久 journal 的真实关联。

无法确认恢复结果时，用户应看见可用的人工核对入口及“未确认”，不能强行重放旧几何。代码默认关闭也可能参与编译和初始化，因此没有硬件不能省掉整 App 构建。

## 收尾交回格式

每个实际提交留：文件差异、基线与候选哈希、完整编译命令及退出码、真实或替身环境、故障前后状态、是否残留窗口/进程、未完成调用者。截图只能证明拍到的时刻，不能替代撤销与恢复记录。宏观进度不按已经写到第几份计算，详见 COMPLETION-CONTRACT。
