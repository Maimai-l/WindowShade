# 10　故障恢复与交付可信度

## 用反例保护后续实现

每个状态边界至少一个反例：恰好到期、刚锁屏、相同名字不同设备、旧连接回复、列表换序、目录重建、写一半断管、Keychain 写失败、AX 读不到、同一确认消费两次。反例不要求概率高；它用来证明实现依赖的是正确事实，而不是理想顺序。

安排反例时使用注入时钟和受控事件序列。需要真实系统语义的地方再用子进程、文件系统和设备测试。不能把所有测试换成 Fake 系统然后得出端到端结论。第六份目录测试真实创建符号链接和替换目录；管道测试真实运行 Python；两者都没有操作用户 home、真实 CLI 或桌面窗口。

## 正向通过、预期拒绝和未通过验收要区分

错误基线被 stage 工具拒绝是保护机制正常；这是预期负例。PROC04 要求尽早识别直接子进程退出，却观察到延迟，是功能验证缺口。它不能写成“成功验证能够失败”后算通过。没有 Mac 的 runner 返回 78 是未运行，不是失败也不是通过。依赖下载失败是准备失败，不是编译错误。

`tools/readiness.py` 对证据文件检查来源版本、真实命令、状态、运行环境、日志路径及哈希。它只能确保材料齐备并且相互对应，不能自动判断一段日志是否证明安全行为。因此自测 fixture 的 PASS 不允许替代 Mac/hardware 阶段；手工审核的结论要有责任人和记录。

## 合并不能靠覆盖

这份 overlay 只适用于确切第五份的 1140 文件基线。源码 manifest 每个路径有旧 hash 和新 hash，stage 先核对整个文件集，拒绝旧目标、基线内部目标和不匹配的工作区。实际开发已前进时，按旧文件、当前文件、本份文件做三方合并，记录冲突的语义，不把当前目录清空来获得“干净通过”。

统一 v6 包已经完成组合，不再依次运行 part1…part6 的 stage。旧份保留为背景和历史证据。新代码-map 用行号帮助定位，执行时先核对 hash；版本变化后行号仅供参考，不能盲贴到相同行号。

## 协议和依赖升级

当前官方文档、当前库 HEAD 与上传 schema 是三个不同版本来源。执行者不能为解决一个字段报错自动升级 CLI 或引入主干依赖。新版本单列兼容分支：读取该版本实际 schema，生成差异，更新 fixtures，跑允许与拒绝两种响应，然后实际连接。未得到兼容证据前保留已固定版本。

可选 SRP 库仍在隔离目录。不自造锁文件，不把一份 Python 参考通过当作 Swift 依赖通过，也不把外部库的自我互测当作原生 Remote 互操作。密码学代码、协议角色、密钥保存和 UI 同意分别审核。

## 影片和发布沿用真实边界

已有两条 126 秒无声动态分镜只是以前的成果。第六份没有新增成片、声音或真机录屏。任何新功能只有满足源码、平台和实际路径证据才允许拍成能力演示；否则继续标概念或待录。不能用本次修好的纯核心生成假的“配对成功”“已解锁”画面。

17 项真实素材、声音授权/混音、正式 Remotion 编译和观感验收仍按原工作单。没有发布授权，不改 1.0.16、更新源、签名身份或真实 home。交付说明以本次实际做过的命令为准，不把前五份的测试数重新累加成第六份成绩。
