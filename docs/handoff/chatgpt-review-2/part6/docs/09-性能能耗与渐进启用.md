# 09　性能、能耗与渐进启用

本篇的所有数值是建议预算或继承的项目默认，不是实测功耗。运行报告不得把它们写成性能成绩。

## 对吞吐量和交互延迟分别设账

本项目的活动数量不大，但窗口采样、控制器回调、屏幕截图和模型事件可能同时到来。逐个小对象分配和重复重建 UI 会让“单次不慢”的工作叠在一起。建议 MainActor 一次只做边界核对、轻量 reducer 和差量呈现；图像、模型、压缩和重计算不放在按键回调里。

第六份进程每次读写 readiness 的预算 64 KiB，诊断保留最多 64 KiB，网络总排队 512 KiB。公平回调预算控制一次占用，保留上限控制内存，它们不是同一个数值。达到队列上限时采取背压或关闭该连接，不能静默丢一半批准帧后继续发送。

## 把持续唤醒变成按需唤醒

番茄钟显示可以一秒更新一次，离屏后停止绘制，不需要每帧运行整个状态机。截止任务按最早待处理事件安排，不每 10ms 扫描所有模块。网络活跃时保留读事件，功能关闭时移除 Listener、Source 和 handler。手柄关闭后不继续采集运动数据来更新不可见视图。

截图、窗口列表、菜单标题缓存和设备读数分别设刷新原因；一个窗口名称变化不应触发所有屏幕重新截图。先追踪重复注册的观察者、取消不了的 Task、永远不清的 handler 和 NSView，再讨论微小算法优化。这些长期对象在“设置默认关闭”的情况下仍可能工作。

## 可重复的对照方案

同一台 Mac、同一 OS 和构建、同一电源条件、相同显示器与外设、相同后台应用，交替运行原 1.0.15 基线和当前候选。先采空闲，再采正常使用和故障条件；每种条件建议三次。记录 wall time、CPU time、wakeups、内存、数据率和可见卡顿，并保留原始工具输出及采集命令。

建议每段十分钟，预热两分钟；这是为了减少一次短峰值的误导，不保证统计充分。不要比较不同机器截图里的 Energy Impact 数字后宣称降低了百分之几十。外设断连、拒绝权限、后台没有客户端、锁屏及睡眠恢复也要跑，因为泄漏常出现在非正常路径。

## 功能准入按真实能力，而不是一把总开关

每个功能保存 source/build/runtime 三种证据。UI 的 availability 由事实产生：设备不存在、权限未给、后端尚未启动、目标不存在、能力未实测、正在认证、正在停止，应有不同原因。显示不可用的原因即可，不因一个模块未准入而把无关的计时器也关闭。

稳定的第一条 owned CLI 路径可以独立启用，配对实验保持关闭。只读查询先验证，命令批准后验证，设备控制再验证。退出失败的模块可以撤回入口但不能把残留状态删掉；用户仍需要看到是否可能有后台任务未结束。

## 编译门禁也要如实

原 `build.sh --check` 实际包含 Metal、优化 Swift 编译和链接，并非简单 typecheck。本次修正说明并为干净目录补 `.build` 创建，避免 mktemp 的父目录不存在。脚本是否解析正确与 Mac 链接是否通过分开记录。

检查需要 Sparkle 时应准备真实框架，不为了过门禁把它的相关文件排除后仍称完整 App 已构建。新的 Foundation 文件已经在 Linux 严格 Swift 6 下组合检查；这不能覆盖 Network、Cocoa、Security、CryptoKit 或私有 SDK 分支。
