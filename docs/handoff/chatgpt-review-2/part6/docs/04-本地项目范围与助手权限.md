# 04　本地项目范围与助手权限

## cwd 字符串只是一条路径

`/work/repo` 与 `/work/repo-backup` 有相同前缀，但后者不是前者的子目录。目录被删除重建后，路径没有变，文件对象已经换了。符号链接又可能把用户看见的路径指向另外一个位置。第六份的 `WS2ProjectDirectory.read` 记录解析后的绝对路径、设备号和 inode；`contains` 按路径分隔边界比较，拒绝未解析的 `..`。

这个观察仍然不是文件系统沙盒。目录在检查后还可能被替换，子目录里的链接也可能变化，CLI 还可能根据配置读取其他路径。因此 Scope 的作用是防止旧 UI/旧连接跨项目，不能把它宣传为文件系统访问隔离。不要使用 `hasPrefix(root)` 决定网络请求是否可以访问任意文件。

## 本地选择与不可变 ticket

项目只能来自本机目录选择器及其实际读取结果，不能从 CLI payload、蓝牙设备名或远端路径字符串创建。持久 projectID 用本地 UUID；名称只用于显示，不参与判定。恢复上次选择时重新读身份，身份不匹配就请用户重新选择，不能悄悄跟随被替换的目录。

`WS2OwnedScope` 初始 locked/disabled，没有 active ticket。用户启用后由 Runtime 写入实际环境；每次 select、begin、invalidate、锁态或 enabled 变化均清除旧 ticket 并推进 revision。重新解锁只改变环境，不复活旧连接。`context` 只在当前 ticket 与实时目录身份一致且 backend session 合法时返回既有 `WS2.Context`，继续复用共享类型。

根目录观察可能发生磁盘 I/O，不要在每个摇杆采样中调用。推荐在选择、启动、批准准备及最终提交前的独立校验阶段读取，并通过统一 revision 撤销路径变化。频繁写入循环仍要复核缓存 ticket 和锁态；缓存不能被文案称为再次读取了磁盘。主模型需要明确接受剩余路径竞争，或者引入具备目录句柄约束的监督端口。

## 本次修复：不继承宽泛的助手设置

第五份 `CodexWire.startThread` 只传 cwd/model，resume 只传 threadId。实际生效的执行权限因此可能依赖外部配置。第六份给新建和恢复 thread 明确传 `sandbox:"read-only"`、`approvalPolicy:"on-request"`、`approvalsReviewer:"user"`。开始 turn 时明确传 readOnly 的 sandboxPolicy，networkAccess=false，并重复人工 reviewer 和按请求审批。

这组字段由上传的 0.153.0 schema 实际核对，四条真实编码出来的 params 通过 schema 检查。它是本项目 V1 保守配置，不是对 Codex 所有版本的事实承诺。没有运行真实 CLI，所以未宣称沙盒实际执行、平台后端或自定义工具都受到了验证。

read-only 并不等于只允许读当前项目；networkAccess=false 也不能描述成整个宿主应用离线。模型服务连接与工具执行网络是不同路径。MCP、外部工具、技能和用户配置需另做准入，第一条真实闭环只使用隔离的、已检查配置。读取配置后发现功能无法收窄时停止启动，不用“相信用户配置”让这条验证通过。

## 普通命令的一次性批准

继续由 `WS2CodexApprovalHost` 展示完整原始命令、cwd、上下文，再交原生认证和 `AuthorizationService.consume`。Scope、设备已配对、按键新鲜、UI 有租约都不产生批准权。固定 profile 不撤销已有的逐条批准设计；它不允许自动 reviewer 替用户作决定。

文件 diff、网络范围和持久规则批准仍未得到完整可信 UI 与 scope。遇到这些请求按已有拒绝策略处理，并显示具体不支持的种类。不要生成空 diff 后称用户批准过文件内容；不要把一次命令批准升级成整目录写权限。

恢复 thread 还有额外工作：验证返回的 thread 与本地项目关联、配置和本次连接一致。Wire 对 thread ID 的检查无法替代这些事实。缺关联证据时允许从本地新建安全 thread，不自动恢复一个看起来名字相同的旧 thread。
