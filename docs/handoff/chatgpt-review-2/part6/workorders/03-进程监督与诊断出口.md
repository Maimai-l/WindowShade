# 工单 03　进程监督与诊断出口

## 已有接口

`prototype/Support/WS2DuplexProcess.swift` 新增 `Termination(status:wasSignalled:)`、`termination`、可选 `diagnosticByteLimit`、`diagnostics`、`clearDiagnostics()`，保留 `onEnd`、`onLine`、`onLocallyWritten`。退出信息和管道停止独立，source 的文件描述符仍在 cancel handler 关闭。背景 docs/03。

## 先运行已提供的真实复现

在 v6 候选执行 `bash tests/run-process.sh ...` 与 `bash tests/run-exit-probe.sh ...`。前者九个正向场景应退出 0。后者当前 Linux 实际退出 2，是未闭合的直接退出观察问题；不要改阈值让本轮报告变绿。Mac 同样运行，再决定 Foundation 是否满足本平台接入条件。

必须保留“父进程写出一行后退出、短命子孙持有描述符”的用例。删除 fork、让子孙提前关闭 stdout 或让父进程等它结束，都会消除原故障条件，不能拿改过的测试代替。

## 接到原生 UI

为本次启动提供本地“保留诊断”选项，默认关。开启时建议 16 KiB，上限 64 KiB。OwnedCodexSession 要把明确选择传给 DuplexProcess，而非从远端参数接受该开关。结束后在用户明确打开详情时显示纯文本尾部、退出码/信号和“仅保留末尾，可能不完整”。不要默认把原始输出传给 GPT/Claude。

关闭诊断视图不自动导出；用户可清除。锁屏和功能关闭立即清除可见内容；是否保留本次内存尾部由明确策略控制，默认清除。退出状态尚未取得时显示“已断开，进程状态未知”。收到真正退出信息后才显示退出码；没有退出码就不造一个 0。

## 监督端口准入决定

如果 Foundation 探针满足平台要求，可保留此后端，但仍不承诺进程树被杀掉。如果不满足，另建隔离 helper，严格做到：由 helper 自己 spawn、自己登记 PID/进程组和启动身份、自己 wait/reap、自己承担取消升级。不要让 helper wait Foundation 的 child，也不要让 Foundation 继续管理 helper 内部的孙进程。

建议监督状态包含 directlyExited 与 descendantsUnknown 两个事实。SIGTERM 后建议 2 秒进入需进一步处理状态；自动 SIGKILL 仅在创建和所有权证据完整的隔离进程组里实现，并单独验收。这个 2 秒是待实现建议，不是第六份已有代码。

拒绝系统全局按名称 kill、对用户已有会话 kill、延迟使用未经身份核对的 PID、无权限时尝试 sudo。没有合法监督端口时保留“结果未知”和人工停止说明，不启用宣称可靠自动退出的能力。

## 收工材料

九项管道测试、PROC04 独立记录、错误输出洪水的 UI 可响应记录、停止后是否仍有 helper/子孙进程的进程树记录、每个 fd 关闭和 callback 取消的路径说明。不得用 `Process.terminate()` 的调用记录代替退出证据。
