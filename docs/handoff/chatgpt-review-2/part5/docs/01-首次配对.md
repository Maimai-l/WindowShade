# 首次配对：把密码学、协议字节和权限分开判断

## 要建立的是哪一种关系

在这条链中 Mac 是待控制的服务端，控制端掌握刚由本地用户确认的 PIN。首次配对建立长期标识和公钥；后续 Pair-Verify 证明连接端仍持有相应私钥，并协商这次连接的密钥。它不证明持有手机的人是哪一个自然人，也不等于批准某条开发命令。设备登录权限不能兑换 AuthorizationService 的命令授权。

原工程有 PairingAttemptWindow、PairingTLV、Pair-Verify、帧和 AEAD 候选，本次补内层 Pair-Setup 编排和持久登记顺序。TCP/OPACK 的入口仍须严格按连接状态分流，不能从一个解密成功的 frame 直接跳到 UI intent。见本地 code-map、[S01][S04][S05]。

## 四位 PIN 为什么不能“哈希一下传过去”

四位数只有有限候选；知道公开盐和简单密码哈希的人可以离线逐个试。这里选择与目标协议相符的 SRP 候选，目标是不在协议中发送可直接离线验证 PIN 的简单凭据。SRP 也不能替你完成限速、用户在场、身份公钥绑定和应用范围限制。因此失败计数必须在服务端本机全局维护，而不是每个新连接一个计数器。

本次规则继承代码：PIN 为恰好四个 ASCII 数字，前导零保留；窗口 60 秒；累计 3 次失败后冷却 300 秒。PIN 只在内存和本机批准界面存在，不写日志、剪贴板、URL、Bonjour TXT 或诊断附件。beginPairing 的持久标记写成功后才把 PIN 返回给界面。重启发现失败或未完成标记，就开始新的 300 秒冷却。重复重启不会加速试码。

这会给一次无害崩溃带来冷却成本，是明确的保守选择。不能用客户端发送的时间戳取消冷却。WS2PairingAdmission 必须是进程唯一实例，网络换连接不能 new 一个空白实例。单连接只能 claim 一个窗口，连接断开、签名失败、存储失败要结算旧 claim；非法匿名探测尚未 claim 时不应无限累计别人的密码失败，但仍须监听级连接配额。

## 内层六步与不可逆点

|接收|必须已经成立|本机动作|允许发出的响应|
|---|---|---|---|
|M1：method=0，state=1|本地 PIN 窗、未占用、登记仓库可读写|占用 connectionID，生成临时 SRP 数据|M2 的盐和 B|
|M3：state=3、A、proof|同一连接和窗口未过期|校验公共值与证明，导出原始会话密钥|M4 的服务端证明|
|M5：state=5、密文|M3 通过、同一个临时状态|认证解密；验证控制端长期公钥签名；构造 M6；持久保存 peer|持久保存成功后才发 M6|

每个输入只消费一次；乱序、重复、过期、字段非法直接关闭这份临时状态。M3 昂贵计算后再检查截止，M5 验证和保存前后同样检查。不要把协议外层消息编号与内层 state 混成一个枚举。TLV 分片由已有 PairingTLV 负责，应用仍检查允许的 tag 和合并后的长度。

保存后 M6 在网络上丢失是合法失败窗口。Mac 已保存 peer，但对端未必得到它。仓库记 awaitingVerification，UI 写“已保存，等待首次连接”，不能写“已连接”。一次新的 Pair-Verify 和应用 session 成功之前不路由命令。重复 M5 不返回缓存 M6，不重用 nonce 或临时状态。同一标识重新配对必须有独立的本地恢复流程，当前仓库故意拒绝覆盖；详见施工单的尚缺项。

## 大整数相同，字节却不一定相同

RFC 5054 给出数学背景和标准组，不能单凭 RFC 标签确认 Companion 的整套证明字节。选用候选组 N=3072 位、g=5、SHA-512，与已读开源协议实现的观测相符；用户名按字面 UTF-8 `Pair-Setup`。RFC 附录 B 的 SHA-1/1024 向量只用于验证参考算式的 k/x，不称为这个组合的完整向量。[S01][S04][S05]

本包候选明确区分：计算 u 时 A/B 补到 384 字节；证明中的 A/B 和共享数 S 的编码按候选最短大端规则处理；K 是 SHA-512 输出的 64 个原始字节，不是 128 字节十六进制文本。候选适配器绕开外部库的便利 proof API，因为该 API 明确会对 A/B/S 做补零。仅关闭 g 的 proof padding 并不改变其余三项。[S02][S03]

这些选择必须通过独立实现和真实对端确认。`reference/srp_reference.py` 提供一个独立 Python 计算，含 A 很短、有前导补零差异的场景；它不是侧信道安全的大整数实现，不进入生产。当前参考测试没有对原生 Remote，也没有对完整 Swift SRP adapter 运行。别把两个使用相同错误编码的自写客户端/服务端互通当成外部证明。

公共值先限长再转大整数；拒绝零、非规范域、模 N 为零以及 u=0。私有随机值由合格密码学库生成；不拿 PIN、时间、设备名或进程号生成 b。秘密值相等比较不得使用会按首个不同字节提前退出的普通比较。数据清引用不等于保证堆内存清零；Swift/CryptoKit 的秘密生命周期限制要如实记录。

## M5/M6 的签名层

本次 WS2PairSetupCrypto 用固定持久本机 seed 创建签名密钥，核验控制端签名绑定的派生值、标识和公钥，再构造自己的 M6。人工向量涵盖合法加密但签名错误的消息，防止把 AEAD 成功当成长期身份签名也成功。tag 17 描述信息只允许有限长度，不用于更换身份、授予管理员权限或写日志。[S05]

`KnownKeySRP` 仅在 Mac 测试中提供固定 K，以测试真实 CryptoKit 签名/AEAD 层。它不能混入 App target。测试通过时也只证明这层与人工向量一致；完整 SRP、原生控制端与传输仍有自己的门禁。

## 依赖决定

候选外部库固定到源码提交，不追随 main；适配器保留在 optional-srp。隔离探针只生成文件，不自动访问网络。Mac 上解析后保存 Package.resolved、传递依赖许可证与真实编译输出；审查 BigNum 的实际后端和模幂侧信道特征，再决定入主工程。锁了最上游 revision 并不等于传递依赖都已锁定，更不等于做过密码学审计。
