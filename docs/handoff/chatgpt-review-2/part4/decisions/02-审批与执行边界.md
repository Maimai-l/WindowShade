# A2 / A4 / D6：审阅、身份验证、消费票据、写到进程是四个步骤

## 这次的批准路径到底到哪里

本份给出一条候选链：CodexWire 中收到请求；WS2ApprovalReview 固化实际目标；WS2CommandReviewView 显示完整命令和上下文；用户新操作后交给原 NotchAuthenticationController；成功后调用既有 AuthorizationService.consume；最后只为同一个 pending 请求编码一次 `accept`。它没有创建旁路授权账，没有发明新的身份判定。

但是 `WS2CodexApprovalHost.deliver` 仍需由真实 owned 进程 transport 实现。函数签名存在、JSON 能编码、Touch ID 的旧实现存在，都不等于这四步已经在一次真实运行中闭合。本轮没有启动 CLI。后续验收要分别记录 review-ready、native authorization、grant consumed、writer admitted、bytes written、backend terminal event，不能把任何中间步骤显示成“执行完成”。

## 固定协议里容易读错的部分

S1 的普通命令审批必填有 itemId/startedAtMs/threadId/turnId；command 和 cwd 在 schema 中可以缺省或为空。因此“schema 合法”不保证用户在这里拥有足够资料批准。我们的 V1 比 schema 更窄，要求完整非空 command、绝对 cwd，以及当前真实线程和轮次。缺失则拒绝，并说明资料不足。

同一 item 也可能有不同审批请求，必须以连接 UUID + typed JSON-RPC id + thread/turn + 精确 params 定位。7 与字符串 "7" 不能合并；展示名称、审批摘要、进程 cwd 不能取代 provider/session/epoch。itemId 不能直接当跨连接授权主键。

文件审批的 params 没有完整 diff。即使其中 reason 写得很具体，仍需从同一后端 item 的权威事件取得实际路径及变更快照，绑定版本后展示。不能自行读取工作区现状猜测“它要改的就是这些”，更不能用摘要替换 diff。文件改动、远端 environment、stdin 审批、网络规则和执行策略修改都不在本份一次性命令批准范围。

## V1 支持矩阵

|请求|当前处理|不要做|
|---|---|---|
|ordinary command，完整 command/cwd 且 scope 匹配|显示完整审阅，新的本机操作后请求真实身份授权|不能用工具描述或低风险标签直接批准|
|命令字段不全、未知 kind、外部环境|owned app-server 返回 decline，显示无法完整确认|不能补猜命令或假设 native prompt 会出现|
|文件变更或持久权限修改|本版不允许；留明确 unsupported 状态|不能 acceptForSession 或改权限配置|
|用户点拒绝|decline 当前命令，保持整个 turn 的语义交给协议|不能把 decline 偷换成 cancel 全 turn|
|用户停止这一轮|独立 turn/interrupt 生命周期|不要借审批拒绝冒充停止|
|schema 新增字段|unsupported 并记录字段名，不记录秘密值|不能忽略新政策字段继续允许|

## 目标绑定为什么必须不可变

`targetBytes()` 包含一个版本化域前缀和逐字段长度，随后包括连接 ID、方法、请求 ID 的类型和值、peer/project/provider/session/epoch、thread/turn，以及排序编码的全部 params。长度前缀避免字符串连接歧义；字段完整避免同样摘要套给不同命令。这里是内部票据目标编码，未宣称采用 RFC 8785 或可对外互通的 JSON canonicalization。

审阅期间收到相同 id 的不同内容不能就地改文本并沿用已开始的确认。必须撤销这次确认，构造新 review。认证完成回调也要重查同一不可变对象、当前上下文、未过期、系统已解锁、请求仍 pending。票据消费到出站入队之间不插入动画 await，不重新读取可变 UI 文本拼装另一条命令。

full command 按纯文本显示，转义不可见控制和双向文本控制字符；不执行 ANSI、HTML、Markdown，不把终端转义当颜色渲染。工作目录、项目和会话也按不可信标签显示。授权目标绑定原始字节；可见转义是为了让人分辨它们，不修改将要执行的命令。

## 新操作的界限

门控先等待 NSView 获得真实窗口、有效 bounds，并且岛停止展开动画，才记 shownAt。此前确认按钮禁用。按下发生在 shownAt 之前而抬起在之后，不能批准；重复键、先前设备 held 状态、第二次同意回调都拒绝。无障碍操作也走新 intent，随后仍需真实身份验证。

VoiceOver 的合法新操作不应被“只能鼠标按下”排除。当前候选按钮为 accessibilityPerformPress 单独生成事件，但 Mac SDK 和实际 VoiceOver 尚未测试。不要为让测试好写直接调用 selector 然后把它算作用户新确认。输入 event 的序号必须在本机产生，不信任对端传来的序号。

## UI 与真实授权的所有权

review 使用 agentReview 的授权层租约，但它本身不签发权限。转交原生认证之前，清掉 review 的取消回调并释放自己的 view；随后由 authorization owner 取得租约。原生授权失败、取消或锁屏，pending review 被拒绝/撤销，不自动退回一个已确认按钮。

旧 backend 断开只取消它仍拥有的 review 或正在进行的认证，不可调用全局 dismiss 把随后打开的番茄钟关掉。本份使用对象身份检查 `dismiss(ifShowing:)`。同理，旧 view 的 cancelOperation 不可作用于后来替换进去的 content。

## Writer 必须实现的契约

`deliver(connectionID, frames, deadline) -> Bool` 中的 Bool **只代表当前连接接受这个有界写入事务，不代表批准、发送完或执行成功**。不允许传一个不检查代次、没有上限的 `Task { write() }; return true`。真实 transport 要做到：

1. 接受前检查连接对象身份、epoch、仍存活、截止、授权环境。每个 owned 子进程只有一个 FIFO writer，UI/后台线程不能竞争写 stdin。
2. 队列条数与字节有上限。建议每连接 128 帧/256 KiB，并同时服从既有 Wire 的单帧限制；超限就停止接收并报告，不丢弃旧允许消息后再执行新的。
3. 每次实际写之前复核连接/截止及应用的撤销 epoch。锁屏、断连、停止进程、撤销设备时清除尚未写的事务。
4. nonblocking 写遇到 EAGAIN 等待可写事件，不主线程睡眠轮询。处理 short write、EINTR、EOF、EPIPE、子进程退出，不能假定 FileHandle 一次写必然完成所有字节。
5. 部分写入后结果不明，关闭这一连接，标记“未确认结果”，不重发 accept。已消费 grant 不补发新票，不自动重跑同一个用户动作。
6. 已经完整写入后，不能承诺锁屏能撤回服务端已经开始的命令。保留请求终态，必要时发独立 interrupt，并等其终态；不伪造回滚。

上面这些是剩余生产接线合同，不是当前候选已完成的网络 I/O 实测。最简单的优先路径是复用前份 owned process 通道，只加一个有界单写者和撤销 epoch；不要另起 localhost HTTP 任意执行服务器。

## Claude 不是换一下 provider 名字就通

S5 区分 PreToolUse 和 PermissionRequest：前者用 permissionDecision；后者用 decision.behavior。当前 PermissionRequest 文档没有 tool_use_id，因此应在实际 hook 每次调用时分配本地请求 UUID，绑定那一个活着的 reply 通道，不能按 command 内容合并两个并发调用。一个看到 SessionStart/Notification 的观察型 hook 并不拥有 stop/approve 权限。

在能够交互的原工具会话中，不接管请求可以继续原有提示；在不能提示的会话里，官方文档说明无决定会导致拒绝。不能统一把 `{}` 称为“自动交回弹窗”。本版不新增 updatedInput/updatedPermissions，避免展示原命令却执行被修改的输入或扩大后续权限。具体 hook 的输出必须遵循正在运行的版本，而不是复制 Codex 的 accept JSON。

## 超时与错误文案

本版 review 从收到完整请求起 30 秒截止。原生身份验证不能把这个期限重新延长。超过期限用“请求已过期，请在原工具重新确认”；资料缺失用“这项操作无法在这里完整确认”；写入不明用“连接中断，尚未确认执行结果”。不写“已阻止所有副作用”，因为失败也可能发生在服务端已经执行以后。

维护一个最多 8 条的 pending review 索引，过载拒绝新请求，不能无限堆积几十个 Touch ID 窗口。一次只展示/验证一条。程序退出和锁屏要立即清空私有审阅内容。日志只记录事件类别、非敏感关联号、错误码和期限，不记录命令正文、完整项目路径或用户草稿。
