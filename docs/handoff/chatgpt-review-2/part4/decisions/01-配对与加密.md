# D5：先分清要连接的东西，再落到字节和生命周期

## 三条链路不能混成一条

实体 Siri Remote 的硬件输入、iPhone 控制中心里的 Apple TV Remote、以及 Mac 上访问助手的本地进程通道是三种来源。实体遥控器能否通过某个 HID profile 产生按键，需要实际设备报告；它不会因为 Companion 的加密测试通过就突然有触点或麦克风。控制中心 Remote 则需要 Mac 实现它认可的发现、配对、会话和命令服务。我们的 owned Codex 只通过受控本地进程通信，不直接暴露成局域网的 shell 服务。U1 要求不新做手机 App，这条边界继续保留。

S2 是一个控制 Apple TV 的客户端实现。把它链接到 WindowShade，方向仍然是“Mac 控制 Apple TV”，不是“手机 Remote 控制 Mac”。本份的 Pair-Verify 独立写了服务端方向，但 **尚未证明原生 Remote 会选择这个入口以及对应 profile**。用手机实际发来的无敏感头部、消息类型、版本协商来判定，不能仅凭广播 `_companion-link` 就标兼容。

## 当前有代码的部分

`WS2CompanionFrame` 处理 type/length/分片；`WS2CompanionCrypto.answerM1` 回答 Pair-Verify，`answerM3` 验证已登记 peer，返回 M4 和受保护会话。输入输出是 OPACK `_pd` 中的 TLV 字节；**OPACK 不由这个类解析**。已认证的记录通过 `VerifiedSession.open`/`seal`，密钥和计数器只在会话对象内。

`Peer` 必须来自可信登记数据库，不是从此次未验证的消息现建一条再返回。`lookup` 找不到就失败；`isCurrent` 每次检查是否仍启用且 revision 相符。只有 answerM3 真正验证成功后才能创建 VerifiedSession；外层不能拿 PIN 是否相等来构造它。

## 为什么首次配对和重连验证分开

PIN 的作用是让首次近场/本机确认建立长期身份关系；后续连接依赖保存的公钥证明掌握对应私钥。首次建立关系的 SRP 流程尚未实现，这不影响独立测试后续证明代码，却意味着产品仍不能宣称配对完成。测试里的固定 peer 是测试前提，绝不能用这些测试 key 初始化实际用户库。

不要用 `SHA256(PIN)` 作为会话密钥，也不要把 PIN 直接发给远端做字符串比较。短 PIN 需要对应的密码认证协议、失败次数限制和本机明确的配对窗口。一个加密过的管道，如果对端公钥是从同一条未验证连接直接信任的，仍不能证明设备身份。

## 服务端 Pair-Verify 状态表

|状态和输入|服务端行为|拒绝条件|
|---|---|---|
|fresh + M1|TLV 6=1、3=32 字节 client ephemeral；产生新的 X25519 临时密钥|未知字段、重复不合法 TLV、错误长度、超时|
|生成 M2|计算共享秘密；派生 proof key；签署 server ephemeral + server ID + client ephemeral；加密身份 TLV|签名/加密失败就关闭|
|proving + M3|TLV 6=3、5=密文；解密 client ID/签名，查已登记 peer|未登记、禁用、revision 失效、签名不匹配|
|生成 M4|返回 TLV 6=4，同时产生分方向保护会话|外层写 M4 失败时关闭会话，不进入命令路由|
|finished 后又 M1/M3|拒绝|不得复用临时密钥启动第二次握手|
|任意失败|关闭状态，释放临时密钥和证明材料引用|不能沿用失败计数状态继续试探|

字节顺序来自 S2 的客户端验证逻辑，服务端行为是本份反向构造。签名材料拼接采用协议指定顺序，不能“统一排序”。Curve25519.Signing 对应 Ed25519；KeyAgreement 对应 X25519，它们不是可互换的同一把钥匙。

## 密钥、nonce 与 AAD 对照

|用途|算法/输入|本份实现|
|---|---|---|
|Pair-Verify 证明加密|HKDF-SHA512，共享秘密；salt=`Pair-Verify-Encrypt-Salt`，info=`Pair-Verify-Encrypt-Info`，32 字节|proofKey|
|M2/M3 的 nonce|4 个零字节 + 8 字节 ASCII `PV-Msg02` / `PV-Msg03`|proofNonce|
|Mac 发给客户端|空 salt，info=`ServerEncrypt-main`|transmit|
|客户端发给 Mac|空 salt，info=`ClientEncrypt-main`|receive|
|main record nonce|8 字节 little-endian counter 在前，后接 4 个零字节|WS2CompanionCounter|
|main record AAD|1 字节 type + 3 字节 big-endian 密文长度，长度包含 16 字节 tag|header(type:8,count:plaintext+16)|
|记录保护|ChaCha20-Poly1305|CryptoKit ChaChaPoly|

proof nonce 与 main record nonce 长度相同，布局却不同。不能照搬 HAP record 的另一种计数布局。收发 counter 各自从 0 开始，前提是双方方向密钥分开且这次共享秘密全新。S3 的要求是同一密钥下 nonce 不重复；不是“只要有计数器就安全”。

认证失败后整个会话关闭。不能 counter 加一继续读下一帧，也不能把同一密钥存盘并让重连 counter 归零。本份在取 nonce 时先占用编号，出错后不重用；最大值前停止，宁可少用一个编号也不回绕。释放 Swift 对象不等于已验证内存全部物理清零，文档不作此承诺。

## 首次 Pair-Setup 还需要补什么

这是生产源码工作，不是只差拿手机试一下。S2 的观察参数为 SRP 的 3072 位组、SHA512、生成元 5、用户名 `Pair-Setup`。其实现还特意区分 S、A、B 的最短大端表示和固定宽度表示。这个编码差异会让“公式正确”却互操作失败。不要看到一份普通 SRP 示例就更换 proof 拼接方式；先用固定向量和目标客户端核对。

后续实施顺序固定如下：先在隔离 Swift 测试目标验证 SRP 算术和证明，再接入 M1/M2、M3/M4 的双向 proof，最后接 M5/M6 的长期身份签名。保留客户端与服务端各自的完整 proof 验证，身份提交最后发生。库只提供算术时，外围 transcript、重放、PIN 尝试计数、提交时机仍由我们负责。

不把 S2 整个客户端库搬进应用。允许先评审一个固定版本的 Swift SRP 算术依赖，在独立测试目录解析依赖、保存 lockfile、核查许可证和传递依赖，然后再由构建脚本显式链接静态模块；不改整个 App 为另一个框架，也不在运行时下载依赖。当前未完成依赖审定，不得伪造 Package.resolved 或填一个未经读取的 commit。执行模型只需完成这个固定入口，无需重新在 Rust/Swift/自制密码库之间选择。

**S2 还有一处不能照搬：读取 M6 的函数解密后提取 serverID/serverLTPK，但所读代码没有验证该身份 TLV 的签名。** 因此它可以提供消息格式线索，不能作为“现成库已完成安全审核”的依据。我们后续客户端互测与服务端 M5/M6 都须检查长期公钥签名和身份绑定，不能让加密成功代替身份验证。

## 持久化和撤销的具体决定

Mac 长期私钥与配对记录进入 Keychain，账号字段使用本地稳定命名空间；UI 显示名仅作标签。偏好文件最多保存非秘密记录索引、启用状态和版本，不保存私钥/PIN/SRP secret。Keychain 失败时显示“未完成配对”，不能退回 UserDefaults 明文。首次配对写入一条待提交记录；双方证明完成后提交 enabled/revision，否则撤销临时记录。旧有效记录不因一次失败重配被覆盖。

删除设备先在内存增加授权 epoch、把 revision/有效性失效，再停止命令路由、清理会话与密钥，最后删除持久化项。磁盘删除失败时仍保持已撤销状态，UI 说明清理待重试。不要仅从列表删除名称却让已持有的 VerifiedSession 继续工作。当前 CryptoKit 会话的 isCurrent 回调已经留好这一条，但实际 Keychain store 和 UI 撤销事务仍要实现。

建议的配对窗口为 60 秒、一次只服务一个用户发起的配对、5 次 PIN 失败后冷却 60 秒。它们是后续 Pair-Setup 的保守策略，不是已跑过的硬件数值，也尚未由本份 Pair-Verify 类实现。错误次数不能通过取消重开清零；这沿用前份 PIN 门控的原则。

## 后续网络适配器必须完成的合同

连接先走 bounded framing，依据当前握手阶段只接受相应类型。未认证时不转发普通 OPACK 命令；验证后不接受明文 command 降级。每条连接独立临时密钥、counter、输入缓冲和 context epoch。read 可以任意拆分，不假定一个回调等于一帧；未知类型/超长/超时立即关闭，保留脱敏原因。

M4 应在加密记录之前按 FIFO 写出；write completion 不能被误认成对端已接收或执行。原生 Remote 的发现 TXT、OPACK 内容、session-start 应答、触摸事件、音频 profile 需要各自证据，不能从“密文能往返”推导全部支持。只先准入已识别的按钮/触摸语义，拒绝任意 shell、文件路径、粘贴密码和改全局授权规则。

## 验收门槛

Python 的 18 项是独立参考计算；MacCryptoTests 是待运行的 Swift/CryptoKit 合成互测。它们应先相符，再用原生 Remote 测首次配对、重连、撤销、错误 PIN、坏 tag、重复帧、取消配对、锁屏、网络切换。真实会话证据保存设备型号、系统 build、构建提交、入口类型、消息种类与相对顺序，不保存 PIN/密钥/完整敏感载荷。任一项不明时，该来源仍不可用于生产动作，但其他已经独立验收的本地番茄钟不必陪着停工。
